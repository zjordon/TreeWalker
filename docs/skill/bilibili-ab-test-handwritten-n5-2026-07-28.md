## 三、核心结论：质量差异在「成功率」维度稳定显现

横向看**成功率**这一列（控制 N 后最稳定）：

- **手写版**：treatment 成功率（100%、80%）**始终高于** baseline（67%、60%），两次都达标（+33pp、+20pp）。
- **蒸馏版**：treatment 成功率（100%、80%）**等于** baseline（100%、80%），两次都 0pp 未达标。

**手写版 skill 稳定提升成功率，蒸馏版不提升。** 这与 [静态质量分析](distilled-skill-quality-2026-07-28.md) 完全一致——手写版有 `upload_file` 直注、`visible=True` 防 decoy、标题框时序等关键省步/避坑指导（兜底难点），蒸馏版缺这 3/5。**静态对比能看出的质量差异，在动态 A/B 的成功率维度得到了验证。**

## 四、指标可靠性分析

| 指标 | 四次表现 | 可靠性 |
|---|---|---|
| **成功率（judge）** | 手写 treatment 稳定 > baseline；蒸馏 treatment = baseline | **✓ 最可靠**——能区分 skill 质量 |
| 封面成功率 | baseline 在 33%/80%/40%/100% 乱跳 | ✗ 噪声大 |
| 步数 | 四次 −24%/+3%/+37%/−24%，无方向 | ✗ 纯噪声 |

**结论：评判 skill 质量用成功率（整体或专项环节），不要用步数。** 步数被 LLM 行为的 run-to-run 随机性主导，样本量不足以稳定区分。

## 五、失败模式观察（skill 兜底多个难点）

baseline 这轮的失败不只在封面：b#4 封面失败、**b#5 创作声明失败**（"下拉菜单组件对程序化点击...失败"）。treatment#3 也只完成 6/7 字段。说明 baseline 可能在**多个难点**（封面、创作声明、标题时序等）卡住，skill 的兜底价值覆盖多个环节，不止封面一个。

## 六、结论演化记录（诚实）

整个验证过程里，结论随数据逐步修正：

1. **手写 N=3 后**：判"skill 达标（+33pp），封面是价值点"——方向对，但 N=3 样本小。
2. **蒸馏 N=3 后**（treatment 步数 +37%）：基于静态对比 + 步数差，过强地判"蒸馏版缺 upload_file 直注导致多走 6 步，质量问题主导"。**这步过度归因了。**
3. **蒸馏 N=5 后**（treatment 步数 −24%，反转）：推翻"步数归因"，转而判"A/B 步数检测不出 skill 质量"。**这步又说过头了**（把"步数不行"扩大成"A/B 不行"）。
4. **手写 N=5 后**（本报告）：四次横向对比后准确化——**步数检测不出，但成功率能**。手写版 skill 在成功率维度稳定显示收益，蒸馏版没有，与静态分析一致。

教训：**单次 A/B（尤其 N=3）的步数/封面差异不可信；要控制变量（同 N 横向对比）+ 看稳定指标（成功率）才能可靠评判 skill 质量。**

## 七、最终方法论（给后续 skill 验证）

1. **评判 skill 质量**：优先**静态对比**（关键省步指导覆盖率、selector 准确性/一致性）+ **A/B 成功率**（不是步数）。
2. **A/B 设计**：同 N 横向对比（手写 vs 蒸馏 vs 无 skill），控制变量；N≥5 才有初步可信度。
3. **失败分析**：读回放 `ab_*.json` 看 agent 在具体环节是否按 skill 指导操作（如封面上传是否用 `upload_file` 直注），比整体指标更能定位 skill 的实际作用。
4. **不要用步数作判据**：LLM 行为随机性 > skill 内容差异，步数差是噪声。
