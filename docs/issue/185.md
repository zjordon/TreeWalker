## 现象

同轮评测中工具层暴露四类可靠性问题（按出现频率排序）：

1. **`evaluate` 长代码在传输中被截断**——高频，至少 3 个任务、两个口径反复踩：
   - task 112（B 轮 steps 15-17）：三次 SyntaxError（`Unexpected end of input` ×2、`Unexpected token '}'`），agent 被迫把代码压缩到极简 arrow-IIFE 才成功；
   - task 64（B 轮）：AJAX 聚合脚本四连败（截断/语法错/裸 `return` 混合）；
   - task 43/122（B 轮）：裸 `return`（无 IIFE 包裹）`Illegal return statement` 重复踩坑——LLM 生成的代码反复带裸 return，错误信息未引导修正。
2. **`read_grid` 无分组计数，数数任务靠上下文手工 tally**——task 64（B 轮，20 步判 0）：对 308 行订单按 `billing_name` 计数，`read_grid` 全量拉取存文件（12.8KB）后只能靠 LLM 分块 tally——计数自相矛盾、内存压缩丢块、相邻同名行被块边界切开漏计（**Emma Davis 被数成 1，实际 2**）。而决定性方法其实存在且便宜（`read_grid` 带 `billing_name` 过滤逐候选复核，B 轮 step 17/18 正是这么做的），缺的是一个原生 `group_count`。
3. **`read_file` 预览截断在 5000 字符**——12.8KB 结构化数据被迫分 3 块读，是上述 tally 漂浮的直接推手。
4. **`read_grid` 对旧版网格（reviewGrid 等 legacy）返回 "no usable row data" 无明确提示**——task 112（B step 6）agent 不知是"该网格不支持"还是"用法错误"，继续尝试。
5. **`screenshot` 对无 DOM 的媒体页（裸 jpg/png URL）返回通用失败**——task 374（B 轮）：agent 三次重试后仍不止损，发明 `document.write` 包 HTML 再截（又败）、再 fetch base64 "验证"字节——为一个无关目标烧 6 步。

## 请求

- [ ] `evaluate` 加传输后**语法预检**：本地 parse 失败即自动修复（包 IIFE、剥裸 return）或返回结构化错误引导，而不是把 SyntaxError 原样扔回 agent 让它猜
- [ ] `read_grid` 原生支持**分组计数**（如 `group_count: billing_name` 一次返回每键计数），把聚合从上下文 tally 中解救出来
- [ ] `read_file` 对 JSON/表格类内容放宽预览上限或提供摘要模式（当前 5000 字符对结构化数据过小）
- [ ] `read_grid` 对 legacy 网格给出明确不兼容提示（agent 免试）
- [ ] `screenshot` 对媒体 URL 给专用错误文案（"媒体文件不可截图"），避免被当作可重试的能力故障

## 评论 · zjordon · 2026-09-13T11:56:56Z

## 收尾总结（`fix/185-tool-layer-reliability`）

**根因分析**（`docs/bug-fix/185-tool-layer-reliability-analysis.md`；探针 `examples/debug_issue185_cdp_shape.py` 于 Chrome 152 实证）：

1. **现象①「传输截断」双根因**：(a) PR #170 的语法自愈从未生效——CDP 编译期 SyntaxError 的语义只在 `exception.description`（`text` 恒为 `"Uncaught"`），匹配源错位，B 轮 52 次 evaluate 失败中 20 次可确定性自愈的失败全漏、18 次截断提示从未触发；(b) 「传输截断」系误诊，真因是 GLM 中长代码（300–800 字符）括号失衡（task_112 step16 的 296 字符代码多 `}` 少 `)` 为反例——截断不会新增 token）。
2. **现象③双截断链**：read_file 窗口 5000 > `display_max_chars` 4000，`ActionResult.__str__` 静默截断且 footer 谎报展示量——每块尾 1000 字符 LLM 永不可见（task_64 Emma Davis 漏计的直接推手）。
3. **现象⑤**：`asyncio.TimeoutError` 的 `str()` 是空串 → agent 只见 `"Screenshot failed: "` 零信息；裸媒体文档等不到合成器新帧必然 10s 超时（task_374 为止损烧 6 步）。
4. **现象②④**：`group_count` 聚合缺失，数数靠上下文 tally 必漂移；legacy/DOM 通道 fields 请求名与显示名表头不匹配时逐 cell 被滤成全空对象行，无任何提示。

**五修复**（38a14a7）+ 第 1 轮 review 七项修正（e9ef67f，第 2 轮 review **0 findings**）：

- **evaluate 自愈复活 + 编译期门控**：err_text 仅在编译期形态（`text=="Uncaught"` 且 `description` 以 `"SyntaxError:"` 开头）参与匹配——运行期异常（含代码内部 eval 抛出的 SyntaxError）不再误触发副作用重跑；单测桩同步改真实 CDP 形状防契约再漂移。
- **screenshot 超时满信息文案**：双成因（裸媒体页/最小化遮挡）+ 出路；仅 guard 开启时归因，传输层 TimeoutError 原样上抛。
- **read_file 诚实窗口**：`min(read_file_max_chars, display_max_chars)` 再减 160 footer 余量——窗口+footer 整体 ≤ 显示上限，续读指针 `use offset=N` 完整可见。⚠️ 行为变更：默认窗口 5000→3840。
- **read_grid `group_count`**：Python 侧 Counter（通道无关、确定性），计数置回显最前且不受落盘分支影响；`counted X of total Y` 未读全警示 + legacy/dom page-local 提示防单页计数被当全局值。
- **三通道「成功但无数据」诊断**：legacy/DOM 全空对象行（附可用表头名单）/ uiregistry 字段名不匹配 / 0 行——且 0 行不再自相矛盾地建议 "retry without filters"（legacy/dom 从不应用 filters）。

**验证**：全量 2634 测 / 覆盖率 90%（>85% 目标）；第 2 轮 code review 0 findings（`docs/bug-fix/code-review/review-issue-185-2.json`）；**真机冒烟通过——B 轮失败任务（112/64/374 等）复跑全部转成功**。

方案文档：`docs/bug-fix/185-tool-layer-reliability-impl-plan.md`（后置不做项见 §8：定界符平衡修复候选、JSON summary 模式、navigate 媒体前置提示）。
