## 二次 §2 机制：为什么"替换"让模型判错上传成功

P0 前：每步 state **累积**，模型上下文里有 state_{N-1}（动作前）+ state_N（动作后），
对比即知"我的上传让画布多了一个 `<img>` 节点" → 判定成功。

P0 后：全局只留 1 份当前 state，模型**丧失前后对比**，只能盯当前 DOM 的噪声信号：
其他空槽位残留的"点击上传文件或拖拽文件到这里"占位文 + Semi UI hidden-input 上传后
重建导致的 input 索引变化 → 误判"上传没生效"→ 死循环换索引。

> 注：browser-use 同样用替换式 state，但有**视觉通道（screenshot）**兜底；TreeWalker
> `include_screenshot=false`（视觉未打通），全靠 DOM 文本，前后对比对它更关键。

## 二次 §3 修复 Option A（已实施）

`src/tree_walker/agent/step.py` `_set_state_message` 改为保留**最近 2 份** state
（previous + current），而非仅 1 份：

```python
state_idxs = [i for i, m in enumerate(self.messages) if m.get(_MSG_TYPE) == TYPE_STATE]
drop = set(state_idxs[:-1])  # 留最近 1 份旧 state，删更老的
self.messages = [m for i, m in enumerate(self.messages) if i not in drop]
self.messages.append({"role": "user", "content": content, _MSG_TYPE: TYPE_STATE})
```

每步 messages = […, state_{N-1}, assistant_{N-1}, state_N, …]。2 份够用（上传判定只需
紧邻的上一步对照）、有界（远小于 P0 前无界累积的 token 成本）。已更新
`tests/test_message_typing.py`（"state 恒 1 条"→"恒 2 条"），1716 测试全过，端到端验证通过。

## 二次 §4 为什么这个问题**只在抖音封面上暴露**

核心：P0 移除的是"前后对比"能力；**只有当某动作的成败在"当前 state 单独看"时就含糊不清，
才会暴露问题**。视频上传 / 普通表单的成功在当前 state 里**自证**，所以不需要前后对比；
封面上传恰好集齐了所有让信号含糊的因素。

### 视频上传（step 1）为什么没事
传完页面**直接跳转**到 `/creator-micro/content/post/video`——`[Current URL]` 变化 +
整套表单换掉 = 当前 state 自带"巨变"信号，模型一眼就知道成功，无需对比。

### 普通表单（input_text / click / select）为什么没事
- **input_text**：工具回显 "Typed 'X'"，且代码**读回 value 校验**（不一致给 `⚠️ Note`）。
- **click**：通常触发可见变化（弹窗开关、跳转、内容出现）。
- **select**：选中项直接显示。
- 元素 index 交互后**稳定不变**。
→ 成功信号在当前 state 单独看就清晰，P0 前后都正常。

### 封面上传为什么"完美踩雷"——5 个含糊因素叠加

| 因素 | 封面模态的具体表现 | 后果 |
|---|---|---|
| **不跳转** | 整个过程停在同一模态、同一 URL | 没有"巨变"信号 |
| **Semi UI 重建 hidden-input** | 上传后 file input **index 变化**（58462→59245→…） | 模型以为"我点的 input 没了 = 选错了" |
| **多槽位共存** | 横/竖/AI/收藏 4 个上传槽在同一模态 | 传完横封面后，**竖封面槽的"点击上传文件或拖拽文件到这里"占位文仍在 DOM** → 模型误判"上传区还空着" |
| **React 渲染预览，无标准 value** | 成功标志是画布渲染一个 `<img>`/canvas，不是 file input 的 value | 模型得在 ~3500 个 DOM 节点里找出"新增的那个 img"，被噪声淹没 |
| **工具回显本身含糊** | "Uploaded 'heng.png' ⚠️ ...if wrong, retry..." | 既说成功又暗示重试，无法自证 |

每个单独都不致命；叠加后：当前 state 里"画布多了个 img"被"占位文 + 变化 index + hedged
回显"三重噪声盖过。P0 前模型用 state_{N-1}（空画布）vs state_N（有 img）的对比把信号从
噪声里拣出来；P0 拿掉对照，模型只剩噪声 → 误判 → 死循环。

### 推论：不只是抖音封面

任何"效果细微 + 不跳转 + 当前 state 有干扰信号 + index 易变"的动作理论上都会中招：
其他 React 多槽位上传器（头像/图册/B 站封面等）、上传后重建 index 的 toggle/switch、
拖拽类操作。抖音封面把这几项占全了，最先暴露。Option A 对所有这类场景都有效——
恢复了前后对比，让模型能把"新增节点"从噪声里识别出来。视频上传/普通表单本来就不依赖
对比，所以无影响、也无副作用。

> **一句话**：不是 P0 专门坏了封面，而是封面是唯一一个"非用前后对比不可"的场景，P0 偏偏把那个对比拿走了。

## 三次 §3 根因：upload_file 的 ActionResult 缺权威页面级证据

`tools/actions.py:_action_upload_file`（行 1459-1622）的回显链：
- L1600 `memory = self._describe_upload(entry, params["index"], file_path)` →
  "Uploaded 'heng.png' to [INPUT] ... at index 7009"。
- L1622 `return ActionResult(extracted_content=memory, long_term_memory=memory)`。

这只回显「**set 成功**」（`DOM.setFileInputFiles` await 返回 OK），**没有页面级验证**。模型
拿到的是"我设置了 input.files"，不是"页面接受了上传、渲染了预览"。结合二次 §4 列的 5 个
含糊因素（不跳转 / input index 变化 / 多槽位占位文噪声 / React 预览无标准 value / 回显本身
hedged），模型即使在 Option A 的前后 state 里看到 canvas 多了一个，也**缺一个权威声音告诉
它"这就是成功"**，转而想用 screenshot 自证——而 screenshot 是残疾的。

## 三次 §4 修复方案：upload_file 页面级验证 + inconclusive 引导（中等改动、低风险）

两层组合，**只在 Act 阶段（upload_file）改，不动 Sense / DOM 序列化**：

### (A) 页面级验证（single-shot 探针，可配置）

上传前用一次 `execute_js` 取 `(canvas_count, img_preview_count)` 快照；`set_file_input` 后
等待短时间再取一次；任一计数增加 → 回显追加 `✅ Upload verified on page: new <canvas>/<img>
preview appeared (count a→b)`。给 LLM **客观证据**。

依据：抖音 canvas 实测在 set 后 ~0.3-0.8s 出现，**一次 ~0.6s 等待 + 一次探针**即可命中，
不做 poll 循环（省掉 ~120 行 polling + backend_id walk 的复杂度与风险）。探针 JS 只用通用
信号（`document.querySelectorAll('canvas')` + `<img>` 的 `blob:`/`data:` src），**不含站点
专属选择器**。

### (B) inconclusive 引导（验证无定论时的死循环解药）

检测不到新 canvas/img 时，回显**明确告诉 LLM**：

> ℹ️ File was set on the input successfully. No new preview detected within the wait
> window — the page may still be processing. **Do NOT conclude the upload failed just
> because the upload area still shows placeholder text like "点击上传文件或拖拽文件到这里"
> — that text is static markup, not upload state.** (This does NOT override explicit
> failure signals — an error toast / "rejected" / 红框 / 文件大小超限 等仍代表真实失败。)
> To confirm, proceed one step and re-read the DOM rather than taking a screenshot
> (visual verification is currently disabled).

这一段直接拆掉「占位文案 → 怀疑 → screenshot」的死链。注意括号里的例外——只豁免"静态占位
文案"，不豁免真实错误信号，避免模型把引导当成"无脑判成功"。

### 为什么不动 DOM 序列化（二次 §4 也讨论过）

`serializer.py:405-436` `_add_input_compound` 已把 file input 的 "File Selected" 暴露给 LLM
（标准浏览器有效，抖音 input cycling 场景无效，已是"能给的都给了"）。死循环根因是
ActionResult 缺权威证据，不是序列化没暴露信号。改序列化会扩大 blast radius（影响每步 DOM
渲染、token、所有 selector_map 测试），性价比低。本期不动。二期备选：给"最近一次 upload
命中的 file input"加 `[recently uploaded]` 标记——仅在一期验证仍偶发误判时再做。

## 四次 §2 探针假阴性根因

`_UPLOAD_PROBE_JS` 只数 `<canvas>` + `blob:`/`data:` 的 `<img>`，且 `_verify_upload`
是**单次**：`sleep(0.6s)` → 探一次 → 比对。抖音封面预览的实际出现时机：在 0.6s 之后、
下一步 state 读取（~10s）之前——**0.6s 窗口系统性错过**（B1 日志 L193：「After waiting,
progress is visible: new canvas elements appeared」，发生在 upload 之后隔一个 step 才看到）。

即探针"假阴性"= 窗口太短 + 单次采样，不是信号选错（抖音确实用 canvas，方向对）。
advisory 兜底让任务仍能成，但探针失去了"报 ✅ 给模型权威确认"的价值。

## 四次 §3 example 不读 env 开关（A/B 设置错误）

`examples/upload_file.py:50` 显式构造 `AgentSettings(...)` 时**没传 `upload_verify_enabled`**，
所以 `load_settings()` 虽然读了 `AGENT_UPLOAD_VERIFY_ENABLED` env，却被 example 丢弃，
`AgentSettings` 字段走 dataclass 默认值 `True`。→ 我的 B 组（设 env=false）实际仍是 ON，
A/B 的 ON/OFF 对照无效。这是设置 A/B 时的疏漏（应先验证开关到达 agent）。

## 四次 §4 修复方案（本期落地）

### Fix 1：探针 polling + 扩信号（治假阴性）

**(a) 扩信号**——`_UPLOAD_PROBE_JS` 增加 `bgPreviews`：用 `[style*="blob:"],[style*="data:"]`
一次性查 inline `background-image` 是 blob/data 的元素（覆盖 React 上传器常用 inline bg-image
渲染预览；原生选择器引擎，O(n) 但快，不遍历全节点跑 getComputedStyle）。返回
`{canvases, imgPreviews, bgPreviews}` 三元组。

**(b) polling 替代单次**——`_verify_upload` 改为：每 `interval_s`（默认 0.25）探一次，命中
任一信号 delta 即早退报 ✅，否则跑到 `wait_s`（默认 **1.5**，原 0.6）预算耗尽报 inconclusive。
早退保证快渲染（<0.5s）不增延迟；慢渲染（0.5-1.5s）现在能逮到；>1.5s 的极慢渲染仍走 advisory
（下一步 state 会看到）。

**(c) 配置**——`AgentSettings.upload_verify_wait_s` 默认 0.6 → **1.5**（总预算）；新增
`upload_verify_interval_s` 默认 **0.25**（poll 间隔）。`Tools.__init__` 同步加 `interval_s` 参数；
`agent.py` 透传。

预期：抖音 canvas 出现在 ~1s 内的多数情况会被报 ✅；advisory 仍作兜底。副作用：上传无预览
页面的 inconclusive 路径从 0.6s 升到 1.5s（可接受；上传不是高频动作）。

### Fix 2：example 透传 env 开关

`examples/upload_file.py` 的 `AgentSettings(...)` 补传 `upload_verify_enabled`、
`upload_verify_wait_s`、`upload_verify_interval_s`（均取自 `settings.agent`），让
`AGENT_UPLOAD_VERIFY_ENABLED` 等 env 真正生效，恢复 A/B 可测性。
